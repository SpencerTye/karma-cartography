# Phase 2 feasibility test: the TEI `max_batch_tokens` limit of Qwen3-Embedding-4B under 21 GiB

## What this test does

It answers one narrow question about serving `Qwen/Qwen3-Embedding-4B` with Hugging Face Text
Embeddings Inference (TEI) on this machine (one NVIDIA GeForce RTX 3090, 24 GB) and this dataset
(the Phase 1 canonical table, 902,144 Reddit messages):

**What is the largest `--max-batch-tokens` value with which the TEI release image serves the
model on batches of the longest real documents without the GPU ever holding more than 21 GiB?**

TEI batches requests by the total number of tokens up to `max_batch_tokens`, so this value is the
one setting that decides how much VRAM a TEI deployment of the model will use. The test measures
it directly: every candidate value runs in a fresh container with an in-process allocation cap
that refuses any allocation past the ceiling, TEI first warms up with a synthetic batch of exactly
that many tokens (its own start-up behaviour), then the longest real documents are submitted so
that TEI forms one batch that fills the budget, and the device total is sampled every 20 ms
throughout. Values are bracketed by doubling, narrowed by bisection on a 512-token grid, and the
final safe value is rerun in a fresh container as a confirmation; the failing value just above it
is a directly measured run, never an extrapolation.

## What it does not do

No full-corpus embedding, no similarity, clustering or indexing, no comparison of embedding
quality, no choice of the final embedding model. Nothing under `../../../data_sample/`,
`../../../legacy/scripts/` or Phase 1 is written to.

## Measurement protocol

- **TEI configuration.** `--model-id <snapshot directory>` (local files, no network),
  `--max-batch-tokens <tested value>`, `--auto-truncate false` (TEI 1.9 truncates by default;
  with truncation disabled TEI refuses to start unless `max_batch_tokens` is at least the
  model's maximum input length, 40,960 = `max_position_embeddings`, because the repository has
  no `sentence_bert_config.json`), `--max-client-batch-size 1024`, `--payload-limit 100000000`,
  `--json-output`. Nothing else is set: TEI's default dtype on CUDA is float16 (the only
  precision its flash Qwen3 implementation accepts; the model card's own Transformers example
  also uses float16), pooling is read from the model's `1_Pooling/config.json` (last token), the
  tokenizer is the model's `tokenizer.json` (it appends `<|endoftext|>`), embeddings are
  L2-normalised by the request's default `normalize: true`, no prompt is applied, nothing is
  quantised, offloaded or truncated (requests send `truncate: false`). Every run's `/info`
  document is recorded.
- **Ceiling.** 21 GiB = 21,504 MiB = 22,548,578,304 bytes of *total device memory* as NVML
  reports it, including the memory held by other processes (the Windows desktop holds 0.9 to
  2.2 GB depending on the moment). Under WSL2 the WDDM driver does not refuse allocations past
  the physical VRAM: a probe was allowed to allocate 23.5 GB on the 24 GB card while the driver
  paged to system memory. So the ceiling is enforced *inside* TEI's process by the allocation-cap
  shim `scripts/vram_cap/` (a drop-in `libcuda.so.1`, loaded first through `LD_LIBRARY_PATH`,
  that forwards every driver call and caps the process's *physical* device memory: the live
  bytes of the non-pool allocation calls plus the memory the device's stream-ordered memory
  pool has reserved, which is what `cuMemAllocAsync`, the call candle uses for every tensor,
  consumes; blocks freed during a forward pass stay reserved in the pool until the next
  synchronisation, so the pool's reserved size, not the sum of live tensors, is what occupies
  the GPU). A non-pool request that would pass `VRAM_CAP_BYTES` is refused; a pool request is
  refused outright when the live bytes plus the request would pass the cap, otherwise it is made
  and, if the pool's reserved size has then passed the cap, undone (the untouched block is
  freed on an idle stream and the pool trimmed at once, so the excursion lasts milliseconds)
  and refused, with the bounded transient excursion reported (`max_overshoot_bytes`). A
  request that the pool can only serve by growing past the cap is a genuine failure of TEI at
  that value, so these attempts cannot bias the verdict. Every refusal returns
  `CUDA_ERROR_OUT_OF_MEMORY` inside TEI. The shim also rewrites
  `cuGetProcAddress` so that the CUDA runtime and cuBLAS get the same wrappers. The cap of a
  test is `ceiling - device total just before the container starts - untracked overhead`, where
  the untracked overhead (the CUDA context and module code that no allocation call reports;
  about 820 MiB) is measured once in the calibration run as the device total at rest minus the
  baseline minus the shim's physical bytes. An NVML thread samples the device
  total every 20 ms for the whole test and kills the container if a sample exceeds the
  ceiling (watchdog); when the shim has just logged a refusal the device gets 3 s to come
  back under the ceiling first, so that the refusal is the recorded outcome. A test is a
  **success** only if TEI started (load and warm-up completed
  under the cap), the batch was embedded as one verified batch, and every NVML sample stayed at
  or below the ceiling. A refusal at the cap during start-up or during the batch is a **failure
  at the ceiling**, reported with the device peak reached before it and the shim's refusal
  record. No balloon process occupies the spare VRAM: the probe showed the driver can evict
  such a balloon (or the target) to system memory, so it would not fence anything, and the cap
  already makes the spare VRAM unusable by TEI.
- **Documents.** The 2,000 longest documents by the Phase 2 exact counts (ties by character
  count, then `doc_key`), plus the longest document of every shorter token length down to two
  tokens, so that a budget can always be met exactly. A batch is filled first-fit-decreasing:
  from the longest document down, every document whose count still fits is taken until the
  budget is met. Texts are the canonical `text`, unchanged; nothing synthetic, nothing
  duplicated. TEI's `/tokenize` count equals the stored count for every candidate (checked in
  `prepare`).
- **One batch, proven.** TEI's batching task pulls the queue as soon as one entry arrives, so
  the documents of a request would be split over several batches on an idle server. The
  script therefore sends two single-document blocker requests (the longest document) 30 ms
  apart, which occupy the backend and TEI's one-batch prefetch channel, then the test
  documents in one request; all test documents are queued while the first blocker runs and
  are pulled together. The Prometheus deltas of `te_batch_next_size` and
  `te_batch_next_tokens` (which also record empty polls as 0) must show exactly three
  non-empty batches of sizes 1, 1 and K with a token sum of twice the blocker's count plus the
  batch total, and the request's `x-compute-tokens` header (TEI's own count of the tokens it
  processed) must equal the batch total. An unverified submission is retried up to three
  times; a test whose batch never verifies is inconclusive and repeated, never guessed.
- **Search.** One run below TEI's minimum (32,768) documents the refusal. Then 40,960;
  doubling while runs succeed; bisection between the largest safe and the smallest failing
  value on a 512-token grid until they are 512 apart; then a fresh-container rerun of the safe
  value (confirmation; if it failed it would become the failing bound and bisection would
  continue). Every run is a fresh container with a freshly computed cap.
- **Measures per test.** `max_batch_tokens`, cap and baseline, K and the token count of every
  document, the batch total, TEI's `x-compute-tokens`, the verification, start-up time and the
  log milestones (load, warm-up), the client's wall-clock of the batch request and TEI's
  `x-inference-time` (the backend duration of the batch), `x-queue-time`,
  `x-tokenization-time`, the NVML peak during start-up (load plus the warm-up batch of
  `max_batch_tokens` synthetic tokens) and during the batch, the shim's tracked peak and
  refusal record, the outcome, the container log.

## Results of the delivered run (2026-09-10; `REPORT.md` has every number)

- **Largest directly measured safe `max_batch_tokens`: 92,160.** Its batch: 42 documents, exactly
  92,160 tokens, verified as one TEI batch (`x-compute-tokens` 92,160); peak device total
  21,294.5 MiB in the search run (test 6) and 21,389.0 MiB in the confirmation rerun (test 13),
  both under the 21,504 MiB ceiling; TEI's backend time for the batch 12.0 s and 11.9 s (client
  wall-clock 13.7 s including the two blockers); model load 10.7 s / 12.1 s, warm-up of the
  92,160-token synthetic batch 29.5 s / 28.6 s.
- **Nearest directly measured failing value above it: 92,672** (test 12): the device total
  reached 21,648.7 MiB during the warm-up, 145 MiB over the ceiling for 0.4 s until the watchdog's
  kill took effect; the shim's physical count was still under its cap, so the excess came from
  memory outside the tracked allocations (context and modules) plus the desktop's share.
- **Confirmation:** the safe value succeeded on its rerun. 93,184 succeeded once (test 9,
  peak 21,461.6 MiB) but its confirmation rerun (test 11) reached 21,760.0 MiB and was killed,
  so it was discarded and the search continued below it. Repeated runs of one value differ by
  up to about 300 MiB in their peaks (the desktop's share and the pool's layout), which is why
  the answer had to succeed twice.
- **Every tested value, in order:** 32,768 refused by TEI before any GPU work (below the
  40,960 minimum with truncation disabled); 40,960 success (peak 14,679.9 MiB); 81,920 success
  (20,229.2); 163,840, 122,880, 102,400 and 97,280 refused at the cap inside TEI during the
  warm-up (a pool growth request undone; the device stayed over the ceiling for 40 to 460 ms
  during the rejected attempt, up to 24,347 MiB for the 6.4 GB request of 163,840); 92,160
  success (21,294.5); 94,720 killed by the watchdog (21,607.6); 93,184 success (21,461.6);
  93,696 killed (21,516.3); 93,184 confirmation killed (21,760.0); 92,672 killed (21,648.7);
  92,160 confirmation success (21,389.0). Fourteen containers, 6.5 minutes of search.
- **Calibration:** untracked overhead 134 MiB in this run's calibration (272 MiB in an earlier
  run: the difference is the desktop's own movement during the 25-second start-up); the
  watchdog decided the four failures within about 150 MiB of the ceiling, the cap decided the
  four clear failures. TEI's `/tokenize` count equals the stored count for all 2,445
  candidates (2,000 longest plus one document per shorter length); TEI 1.9.3, git sha
  `06670157fb6c1523482219bdb2d1660277d38088`, image digest `sha256:a7d82dfe...`; model
  revision `5cf2132abc99cad020ac570b19d031efec650f2b`; `/info`: float16, last-token pooling,
  `max_input_length` 40,960, `auto_truncate` false.

## Findings from the sources (read before the runs; TEI v1.9.3)

- `router/src/lib.rs`: the maximum input length comes from `sentence_bert_config.json`
  (absent for this model) or else `config.max_position_embeddings` (40,960); if it exceeds
  `--max-batch-tokens` and `--auto-truncate false` is set, the server refuses to start with
  "Either increase `--max-batch-tokens` to at least `40960`, or set `--auto-truncate true`".
- `router/src/main.rs`: `--auto-truncate` is a boolean argument that defaults to true.
- `backends/src/lib.rs`: on a non-padded (GPU flash) model the warm-up embeds one synthetic batch
  of exactly `max_batch_tokens` tokens, split into sequences of the maximum input length; a
  warm-up error aborts the start ("Model backend is not healthy").
- `core/src/queue.rs`: for a non-padded model the batch is filled while the sum of the entries'
  real token counts stays at or below `max_batch_tokens`; the first entry that does not fit is
  pushed back; `te_batch_next_size` and `te_batch_next_tokens` are recorded on every poll.
- `core/src/infer.rs`: every input of a request is tokenised and queued separately; batches go
  to the backend through a channel of capacity one; a backend error fails the requests of that
  batch with HTTP 424 and the server keeps running.
- `backends/candle/src/lib.rs`, `models/flash_qwen3.rs`: on CUDA with float16 and compute
  capability 80 or more, Qwen3 runs as `FlashQwen3Model` (varlen flash attention, `is_padded()`
  false); the candle backend accepts only float16 and float32.
- `router/src/http/server.rs`: a multi-input `/embed` response carries `x-compute-tokens` (sum
  over the inputs) and per-input averaged times; `/metrics` is served on the main port (the
  `--prometheus-port` listener is never started); backend errors map to HTTP 424.

## Known limitations

1. The allocation cap counts the bytes requested through the driver's allocation entry points
   (`cuMemAlloc`, `cuMemAllocAsync`, pool, pitch, managed, `cuMemCreate`); the CUDA context,
   module code and the stream-ordered pool's retained memory are outside it and are covered by
   the calibrated untracked overhead and by the NVML verification of every sample. A test whose
   device total exceeded the ceiling would be recorded as a failure even if TEI itself did not
   fail (`device_peak_over_ceiling`); none did in the delivered run unless the table says so.
2. Memory held by other processes (the Windows desktop) counts against the ceiling and changes
   between runs (recorded per test as `device_used_before_start_mib`); the cap is recomputed
   from it for every container.
3. Wall-clock times are single measurements on a shared desktop machine.
4. The warm-up batch consists of synthetic sequences of up to 40,960 tokens; it is TEI's own
   start-up behaviour and is part of what "running TEI at this `max_batch_tokens`" costs, so a
   value whose warm-up does not fit is a failure even though its real batches would be shorter.
5. The result is specific to TEI 1.9.3's candle implementation (float16, flash attention v2,
   no caching allocator) on this GPU and driver; it is not a statement about other servers,
   precisions or GPUs.
6. The sidecar hashes are of the files as the script wrote them in WSL2 (LF line endings).
   The repository's `core.autocrlf=true` rewrites text outputs (CSV, JSON, Markdown, logs) to
   CRLF on a fresh checkout, so their hashes match the sidecars only in this working copy or
   after `git checkout` with `core.autocrlf=false`; the scripts and the C source are pinned to
   LF by the folder's `.gitattributes`, so their hashes always match.
