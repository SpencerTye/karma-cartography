# Phase 2 feasibility test: Qwen3-Embedding-4B and 8B on the worst-case documents

## What this test does

It answers two narrow questions about the two candidate embedding models,
`Qwen/Qwen3-Embedding-4B` and `Qwen/Qwen3-Embedding-8B`, on this machine (one NVIDIA GeForce
RTX 3090, 24 GB) and this dataset (the Phase 1 canonical table, 902,144 Reddit messages):

1. **How long is every document in the models' own tokens?** Every one of the 902,144 texts
   is tokenised with the exact tokenizer the models use, and the eight longest documents are
   listed with their exact token counts and whether they fit the models' supported input length
   (32k tokens per the model cards).
2. **What does embedding the worst-case documents actually cost?** Each model is loaded
   unquantised in BF16 and asked to embed the single longest document (Case A), the three
   longest in one padded batch (Case B) and the eight longest in one padded batch (Case C),
   each as one forward pass, with no truncation. VRAM, RAM and wall-clock are measured, and the
   GPU is held to a 21 GiB ceiling of total device memory.

Every number in the results is measured. The test estimates nothing, extrapolates nothing,
embeds no more than the eight documents per model, and does not choose between the models.

## What it does not do

No full-corpus embedding, no similarity, clustering or indexing, no production batch size,
no full-corpus runtime, no model selection. Those belong to the Phase 2 build, which will start
from these measurements.

## How to run

Build the environment once (installs `uv`, the venv, the libraries, downloads both snapshots at
the pinned revisions, verifies the blobs; about 30 GB of downloads):

```
wsl -d Ubuntu-24.04 -- bash -lc "bash '$REPO/pipeline/phase2_semantic_embeddings/feasibility_qwen3_embedding_worst_case/scripts/setup_wsl2_env.sh'"
```

Run the whole test (tokens stage, then each model in its own process, then the report):

```
wsl -d Ubuntu-24.04 -- bash -lc "~/venvs/socialmediadgg-phase2/bin/python '$REPO/pipeline/phase2_semantic_embeddings/feasibility_qwen3_embedding_worst_case/scripts/phase2_feasibility_qwen3_worst_case.py' --stage all"
```

Stages can be run separately: `--stage tokens`, `--stage bench --model 4B`,
`--stage bench --model 8B`, `--stage report`. Parameters (all with defaults): `--project-dir`,
`--expected-rows 902144`, `--supported-length 32768`, `--vram-ceiling-mib 21504`, `--top-n 8`,
`--tokenize-batch-size 4096`, `--sample-size 2000`, `--seed 20260909`, `--nvml-interval-ms 20`,
`--no-profiler-replay`. The script finds the project root from its own location.

Unit test of the pure functions (synthetic inputs, no data, no GPU, about two seconds):

```
wsl -d Ubuntu-24.04 -- bash -lc "~/venvs/socialmediadgg-phase2/bin/python '$REPO/pipeline/phase2_semantic_embeddings/feasibility_qwen3_embedding_worst_case/tests/test_phase2_feasibility_functions.py'"
```

## Measurement protocol

- **Implementation.** The model card's "Transformers Usage": `AutoTokenizer` with
  `padding_side='left'`, `AutoModel` with `attn_implementation="flash_attention_2"` and
  `dtype=torch.bfloat16` on `cuda:0`, one forward pass, `last_token_pool` (verbatim from the
  card), L2 normalisation. The card's example truncates at `max_length=8192`; here nothing is
  truncated and no `max_length` is set. Forward passes run under `torch.inference_mode()`.
  Each model is benchmarked in its own process; the two are never resident together.
- **Ceiling.** 21 GiB = 21,504 MiB = 22,548,578,304 bytes of *total device memory* as NVML and
  `nvidia-smi` report it, which includes the memory held by other processes (the Windows desktop
  holds about 2 GB). After the CUDA context exists, the caching allocator is capped with
  `torch.cuda.set_per_process_memory_fraction` at `ceiling - device memory used at that moment`,
  so the process cannot allocate past the ceiling: a request beyond it raises
  `torch.OutOfMemoryError` instead of spilling into shared system memory, and that failure is the
  recorded result. An NVML thread samples the device total every 20 ms during every case and
  records the peak. Two flags are reported per case: `ran_within_ceiling_21504_mib` (the case
  completed with the device total at or below the ceiling; a case whose allocation was refused at
  the cap is a failure that exceeded the permitted budget) and `device_peak_under_21504_mib` (the
  enforcement evidence: the device total never went above the ceiling). The peak is also compared
  with the decimal reading of 21 GB (21,000,000,000 bytes = 20,027 MiB).
- **Cases.** A: the longest document alone. B: the three longest in one batch. C: the eight
  longest in one batch. Batches are padded on the left to the longest member (`padding=True`,
  no truncation) and go through one `model(...)` call. Before Case A a 16-token warm-up pass
  initialises cuBLAS and the kernels. Between cases: `synchronize`, `empty_cache`,
  `reset_peak_memory_stats`, and the Linux resident high-water mark is reset
  (`/proc/self/clear_refs`) so the RAM peak is per case.
- **Measures per case.** Success or failure with the reason; the token count of every document
  (checked against the tokens stage); the input tensor shape; padded length; padding per
  document; wall-clock of the forward pass (with `torch.cuda.synchronize`), of the host-to-device
  copy and of tokenisation; VRAM after loading (allocator allocated, allocator reserved, device
  total, share attributable to the process); peak device total (NVML), peak allocated, peak
  reserved; increments above the loaded baseline (device total and allocated); peak process RSS
  (high-water mark and 20 ms samples) and peak system memory used; embedding dimension.
- **Cache.** The measured cases pass `use_cache=False`. What the runtime does by default is
  established empirically: a 60-token probe is run with the default setting and with
  `use_cache=False`, and the returned `past_key_values` object is described (type, layers, key
  tensor shape and dtype, bytes); Case A is repeated with the default setting as a
  supplementary measurement.
- **Attention.** Three pieces of evidence: the configuration value, the function that the
  transformers attention registry hands to the model (wrapped to count its calls: one per layer
  per forward pass), and the CUDA kernel names observed when the same input is replayed under
  the torch profiler (a separate pass; its time is reported separately).

## Results of the delivered run (2026-09-09, `REPORT.md` has every number)

- **Data.** 902,144 documents, SHA256 equal to the Phase 1 sidecar; `len(text)` equals Phase 1
  `text_n_chars` for every document.
- **Tokenizer.** The four tokenizer files, the vocabulary, the added and special tokens, the
  post-processor and the encodings of a 2,000-document sample are identical for both models; one
  tokenisation pass (38 s for all documents) therefore serves both. Every input receives one
  appended `<|endoftext|>` token (id 151643), included in the counts.
- **Token lengths.** Median 22 tokens, p99 253, p99.9 640, maximum 5,823 (`t1_oxogwqy`, a
  comment of 2,241 characters). No document exceeds 8,192 tokens; the supported 32,768 is
  never approached. The eight longest: 5,823, 4,863, 3,123, 2,703, 2,703, 2,525, 2,418, 2,228
  tokens, all comments.
- **Qwen3-Embedding-4B** (baseline after loading: 7,671 MiB allocated, 10,200 MiB device total
  including the desktop's share): Case A peak 10,871 MiB device (+671), 1.22 s; Case B
  12,173 MiB (+1,973), 2.76 s; Case C 15,570 MiB (+5,371), 5.92 s. All three cases ran within
  the ceiling. Embedding dimension 2,560.
- **Qwen3-Embedding-8B** (baseline 14,434 MiB allocated, 17,087 MiB device total): Case A
  17,777 MiB (+690), 1.53 s; Case B 19,153 MiB (+2,065), 3.86 s; both within the ceiling.
  Case C failed after 0.35 s: the allocator refused a 1.07 GiB request with 18.55 GiB allowed
  and 17.31 GiB already allocated; the device peaked at 21,096 MiB, under the 21,504 MiB
  enforcement point. Embedding dimension 4,096.
- **Cache.** A call with the configuration default builds a `DynamicCache` (36 layers, keys and
  values in BF16; 819 MiB for the 5,823-token document), which raised the peak allocation of
  Case A from 8,120 to 8,939 MiB (4B) and from 15,037 to 15,855 MiB (8B). With
  `use_cache=False` no cache object is returned. The measured cases pass `use_cache=False`.
- **Attention.** `flash_attention_forward` was called 36 times per forward pass (one per layer)
  and the profiler replays show only `flash::flash_fwd_kernel`.
- **Consistency.** The same document embedded alone, in the batch of three and in the batch of
  eight agrees with cosine 0.9997 or higher (identical within a batch).
- **Timings.** Loading: 20 s (4B), 37 s (8B). Whole run (tokens, both benches, report): under
  four minutes.

## Findings from the installed sources (read before the runs)

- transformers 5.17.0, `models/qwen3/modeling_qwen3.py`: `Qwen3Model.forward` is decorated with
  `@merge_with_config_defaults`, which substitutes `config.use_cache` (True for both models) when
  `use_cache` is not passed; the forward then executes `if use_cache and past_key_values is None:
  past_key_values = DynamicCache(config=self.config)` and returns it. Passing `use_cache=False`
  skips both. The attention function is resolved per layer through
  `ALL_ATTENTION_FUNCTIONS.get_interface(config._attn_implementation, eager_attention_forward)`.
- `integrations/flash_attention.py` and `modeling_flash_attention_utils.py`: `flash_attention_2`
  maps to `flash_attention_forward`, which calls `_flash_attention_forward`; when the batch has any
  padding the inputs are unpadded (`_upad_input`) and `flash_attn_varlen_func` from the
  `flash_attn` package runs; without padding `flash_attn_func` runs. No dense attention mask is
  built for flash attention (`masking_utils.flash_attention_mask` returns None or the 2D mask).
- sentence-transformers 6.0.1, `base/modules/transformer.py`: the encoder module forwards the
  tokenizer features plus `return_dict=True` to the model and passes no `use_cache`, so under
  transformers 5.17 the configuration default applies there. (Read from the source; the
  sentence-transformers path was not run.)

## Known limitations

1. The ceiling is enforced on the allocator of the test process plus a monitor of the device
   total; memory held by other processes (about 2 GB for the Windows desktop) counts against the
   ceiling and can change between runs. Each report row records the device total before the
   CUDA context was created.
2. Under WSL2 the per-process GPU memory is not reported by NVML; the "attributable to the
   process" figure is the device total minus the total observed before the process created its
   CUDA context.
3. Wall-clock times are single measurements on a shared desktop machine, not repeated
   benchmarks.
4. Only the eight longest documents are embedded; nothing is measured about typical documents
   or about the full corpus.
5. PyTorch's out-of-memory message quotes "this process has 17179869184.00 GiB memory in use";
   that figure is an artefact of the per-process NVML query being unavailable under WSL2. The
   device figures in the tables come from the script's own NVML sampling of the device total.
6. Under the decimal reading of the ceiling (21,000,000,000 bytes = 20,027 MiB) the 8B Case C
   peak of 21,096 MiB would also count as exceeding the ceiling; every other case's peak is
   below both readings (8B Case B: 19,153 MiB).
